1. Follow KISS and YAGNI in code and project instructions. Add features, options, or abstractions only for a concrete use in the current task; hypothetical future use and tests written solely for a new feature do not justify it. When referencing upstream, implement only the needed subset and preserve its semantics without adding policies the task does not require. When removing a feature, also remove its unused implementation, exports, configuration, documentation, and tests. Keep instructions actionable, without duplicating existing rules or narrating past incidents.
2. Keep code modular and organize it by functionality. Avoid files containing thousands of lines.
3. When fixing a bug, trace the failure to the underlying flaw in the logic, data flow, or design, explain it, and fix it in the module responsible for the behavior. Aim to remove the cause, not merely suppress errors or add special cases that hide the symptoms. Check related paths affected by the same cause and verify the original triggering scenario. If a workaround is unavoidable, explicitly explain why the root cause cannot yet be fixed and what remains unresolved.
4. Use Chinese only when communicating with the user, including progress updates, reports, root cause explanations, and validation results. Clearly describe what changed, why it changed, and the results of checks actually performed.
5. Use English for code comments and Git commit messages, including both the subject and body.
6. Use ASCII punctuation and symbols instead of Chinese or full-width punctuation and symbols, including in Chinese replies to the user.
7. Backward compatibility is not required anywhere in this project. Target the current design directly; do not add compatibility shims, legacy configuration support, or migration instructions for old versions and deployments.
8. When explaining a bug or writing a review finding, use plain language and a concrete scenario to explain how it is triggered, what should happen, what actually happens, its impact, and the general direction of the fix. Explain necessary technical terms instead of relying on jargon.
9. Write idiomatic, readable code suitable for human review in an open source project. Follow established language and repository conventions, use clear names and straightforward control flow, and avoid opaque or unnecessarily clever code.
10. Keep testing proportional to the change. For bug fixes, add the smallest regression test that reproduces the actual failure; add other cases only for concrete, likely failure modes supported by the code or usage. Do not add redundant tests, speculative edge cases, exhaustive combinations, or tests that merely check simple assignments, pass-through calls, fixed constants, or standard library behavior.
